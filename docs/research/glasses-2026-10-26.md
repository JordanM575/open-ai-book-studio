# Research: Meta glasses as a second surface

**Date:** 2026-10-26
**Spec:** [026](../../specs/026-glasses/spec.md)

## The question

Can AI Book Studio run on Meta's glasses, and can Meta's own assistant use the studio's
integrations? The author has Meta Ray-Ban Display glasses.

## What Meta actually offers, as of 2026-10-26

Read from Meta's own developer documentation and from the Wearables documentation MCP server at
`https://mcp.developer.meta.com/wearables` (the same server Meta's build guide tells developers to
point their coding agents at).

### Three surfaces

| Surface | Source | What it is |
| --- | --- | --- |
| **WebMCP** | `wearables.developer.meta.com/docs/develop/webapps/agent-tools` | A web page registers its actions as tools the glasses' assistant calls by voice, through `document.modelContext`. No SDK, no native app, no new framework. A Community Group standard, not a W3C standard, but implemented and stable on the glasses. Off by default; enabled per device, or by Developer Mode. |
| **Meta AI Connectors** | `dev.meta.ai/products/connectors` | A service is exposed to the Meta AI assistant through **an API or an MCP server**. "No new SDK, no new app to ship." "One integration runs on AI glasses and Meta AI app and web today." Developer preview; access is granted in waves. |
| **Device Access Toolkit 1.0** | `wearables.developer.meta.com/docs/develop/dat` | A native iOS or Android app drives the glasses: camera, microphone, speakers, motion, and the display on the Ray-Ban Display. Stable since 30 September 2026. The only surface that reaches the camera or the microphone. |

### The Web App's constraints, as documented

- Fixed **600×600** viewport, no scrolling. The display is an additive waveguide: black adds no
  light, so use a dark background and light, high-contrast text.
- Input is the D-pad (arrow keys, select, back), optional pinch-and-drag, and the on-glasses
  composer for text. No mouse, no touchscreen, no physical keyboard.
- `window.speechSynthesis` plays through the glasses' speaker. One English voice, no permission
  prompt.
- **No camera, no microphone, no notifications** on a Web App.
- The page **must be served from a publicly accessible HTTPS URL**. "HTTP-only URLs are not
  supported." Hosting it yourself is allowed, over HTTPS with a valid certificate.
- Meta's rule for WebMCP: "Every action you expose as a tool must also be reachable by hand in
  your UI. Treat WebMCP as an accelerator, never as the only path to something."
- There is a **simulator**: a Chrome extension that recreates the 600×600 display and the D-pad,
  so the work can be done without the hardware.

## The one constraint that decides the design

The glasses reach the internet through the phone. They cannot reach the author's laptop on
`127.0.0.1` or on its LAN address, and a browser will not let an HTTPS page fetch an `http://`
one. So prose reaches the glasses in exactly two ways:

1. **Through a public endpoint** — the connector route and the Web App route both need this.
2. **Through the phone** — the Device Access Toolkit app on the phone reaches the author's studio
   over the local network and pushes to the glasses over Bluetooth.

Only the second keeps the author's own book on the author's machine. The first is the only one that
fits the event window, and it is safe only for the **sample library**, which is already committed,
public and original.

## The contract already fits

The studio's `ToolDescriptor` is a name, a description, a JSON Schema and a tier. Meta's shapes
want the same fields, and the mapping is one-to-one:

| Studio | WebMCP | Meta AI connector |
| --- | --- | --- |
| `name` | `name` | `name` |
| `description` | `description` | `description` |
| `inputSchema` | `inputSchema`, stringified | the arguments schema |
| `tier: "read"` | `annotations.readOnlyHint` | classification Read |
| `tier: "destructive"` | `annotations.consequentialHint` | a sensitive write |

Meta's connector guidelines ask for "read/write classifications, sensitive designations,
permissions, side effects, status handling, errors, and rate limits". The studio's tier **is** that
classification, and `bookwriter mcp` already speaks MCP.

**The interchange was already chosen.** The studio is not being translated into Meta's shapes; it
is being renamed into them.

## The live check

`packages/core/src/agent/surfaces.ts` renders the catalog into both shapes, and the toolkit serves
them from a live studio:

```bash
bookwriter tools --format webmcp
bookwriter tools --format connector
```

Run against the built desktop app over its loopback backend with a throwaway library, both
rendered **22 tools**, the studio's whole catalog. A sample of the WebMCP form:

```json
{
  "name": "read_story_bible",
  "title": null,
  "description": "Read the full Story Bible: book description, outline, story arc, every character field …",
  "inputSchema": "{\"$schema\":\"http://json-schema.org/draft-07/schema#\",\"type\":\"object\",\"properties\":{},\"additionalProperties\":false}",
  "annotations": { "readOnlyHint": true, "untrustedContentHint": false, "consequentialHint": false }
}
```

And the connector form for the same tool:

```json
{
  "name": "read_story_bible",
  "classification": "read",
  "sensitive": false,
  "sideEffects": "None. The book is not changed.",
  "errors": "Refuses arguments that do not fit the schema, and refuses a tool the author has withdrawn for this book."
}
```

## What is not proven

- Nothing has been run on the real glasses. The assessment is from Meta's documentation, not from
  the hardware.
- The Web App itself does not exist yet. Only the two shapes of the catalog do.
- The connector has not been applied for, and access is a wave process, so no date can be promised.
- The public instance of the sample library is not built, and whether to publish one at all is
  D-157.
