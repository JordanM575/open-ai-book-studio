# Manual pass: the plugin folder in the real app

**Date:** 2026-10-26
**Spec:** [025](../../specs/025-agent-capabilities/spec.md)
**Command:** `bun run plugin:probe` (after `bun run build`)

## What it proves

The unit tests load a plugin folder in Bun's runtime. The app runs in Electron's main process,
which is Node 24 with the types stripped by Node itself. This pass runs the **built** app, points
it at a throwaway library and a folder of TypeScript plugins, and asks the app's own loopback
backend for its tool catalog and for one plugin tool call.

Nothing touches the author's own library, no provider is called, and the profile and the library
are deleted afterwards.

## What happened

The probe wrote two plugin files into a temporary folder:

- `greeting.ts` — a plugin that needs no import at all. Its arguments are a JSON Schema, so it
  loads without the app's packages being resolvable from the plugin's folder.
- `needs-zod.ts` — a plugin that imports `zod`, which cannot be resolved from a folder outside the
  app. It must fail to load without taking the other plugin with it.

The app was started with a throwaway profile, a throwaway library and the plugin folder set in the
app settings. The probe then asked the backend:

| Check | Result |
| --- | --- |
| The catalog lists the plugin's `say_hello` tool | **yes** — 23 tools, 22 built-in and 1 plugin |
| The plugin's tool actually runs | **yes** — `POST /v1/books/book_probe0001/tools/say_hello` returned `Hello Author` |
| A plugin that cannot load does not take the others with it | **yes** — `say_hello` was still there after `needs-zod.ts` was added |

```
[probe] the catalog has 23 tools; the plugin's say_hello is there
[probe] the plugin's tool ran: yes ({"result":{"ok":true,"message":"Done.","result":{"message":"Hello Author"}}})
[probe] a plugin that cannot load did not take the others with it: yes
[probe] ok
```

## What it does not prove

- A plugin that writes to the book. The unit test covers the write path, and it uses the same
  `Library` the built-in tools use, but the probe did not write prose.
- A plugin in a packaged `.asar` build. The probe ran the unpackaged build. A packaged build has
  the same Node runtime, so the loader behaves the same, but it was not exercised.
- Anything about a plugin that reaches outside the book. The contract does not give it the means,
  and that is a design fact rather than a tested one.

## Notes

- The plugin's tool is a **write**, so the toolkit's `--allow-writes` applies to it exactly as it
  does to a built-in tool.
- The `needs-zod.ts` failure is the reason the contract accepts a JSON Schema. A plugin folder
  usually sits outside the app, where the app's own packages cannot be resolved, so a plugin that
  needed an import would simply fail to load.
