# Toolkit manual pass: the CLI and MCP server against a real library

**Date:** 2026-10-26
**Build:** `meta-hackathon` at `8af33cd`
**Method:** the compiled `bookwriter` binary (`apps/toolkit/dist/bookwriter`) against a real
`LocalBackend` over a real `Library` on disk, in a throwaway directory. No fixture stubs: the
backend ran in-process, the CLI and the MCP server ran as separate processes, and every change was
read back from the file.

## What was run

| Step | Result |
| --- | --- |
| `bookwriter tools` | 22 tools listed with their tier: 6 read, 9 write, 7 destructive |
| `bookwriter call <book> append_to_chapter --args '{"chapterId":"…","text":"A line from the real CLI."}' --allow-writes` | `{"ok":true,"message":"Added the passage to “One”.","chapterId":"ch_…","wordCount":10}` |
| The chapter file on disk afterwards | `"The hall was cold.\n\nA line from the real CLI.\n"` |
| `bookwriter call <book> overwrite_chapter --allow-writes` (no destructive opt-in) | exit 1, `overwrite_chapter can remove or replace work. The caller must allow destructive tools explicitly.` |
| The chapter file after the refused call | unchanged |
| `bookwriter mcp --allow-writes` → `initialize` | protocol version echoed, `serverInfo.name` = `ai-book-studio` |
| `tools/list` | 18 tools: the 3 library-level ones plus 15 studio tools, each with a `bookId` argument |
| `tools/call` `read_story_bible` | `ok: true`, the book's own title and Story Bible |
| `tools/call` `append_to_chapter` | `ok: true`, `Added the passage to “One”.` |
| The chapter file after the MCP call | `"The hall was cold.\n\nA line from a real MCP client.\n"` |

The MCP client was a separate process speaking newline-delimited JSON-RPC 2.0 over the server's
stdin and stdout, exactly as an MCP host would. Diagnostics stayed on stderr; stdout carried only
protocol messages.

## What this proves

- The MCP server exposes the **built-in agent's own tools**, not a second dialect: the same names,
  the same descriptions and the same JSON Schemas, with `bookId` added so one server reaches any
  book in the library.
- A third-party agent can do what the built-in agent does — read the Story Bible, read a chapter,
  append, replace, split, update the cast — with the desktop app remaining the only writer.
- The tier rules hold end to end. A read tool is always available, a write tool needs
  `--allow-writes`, and a destructive tool needs `--allow-destructive` on the client **and** an
  explicit opt-in in the request, so a token on its own is never enough.
- A change made by another agent is reversible: the bridge leaves an undo checkpoint in the same
  format the studio's own Undo reads.

## Not covered

- A hosted MCP client such as Claude Desktop or Cursor. The session above used a hand-written
  client, because the point was to prove the server and the tools, not the host's configuration.
- Concurrent access: two agents writing the same chapter at once. The version and hash guard
  applies as it does to the built-in agent, but the race was not exercised.
- A live Meta key. Nothing in this pass called a provider.
